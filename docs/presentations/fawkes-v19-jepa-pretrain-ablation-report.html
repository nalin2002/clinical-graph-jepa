Clinical Graph-JEPA · Engineering Report No. 3

v19: the JEPA pretraining ablation — does phase 1 do anything?

A reviewer asked how much of the fawkes result comes from JEPA pretraining rather than from having any graph encoder at all. v19 answers it with six arms across three seeds. The answer is not the one the paper assumes, and this report is where that is written down — then §7–§10 work backwards through v18, v17 and v16 so the whole lineage stays traceable from one document.

§1The verdict, first

Phase 1 is not carrying the result. On leave-one-out edge recovery — the paper's own measure — a frozen randomly initialised encoder scores the same as the JEPA-pretrained one, and the identical architecture trained end-to-end without phase 1 beats both by roughly 0.31 MRR. An encoder with its message passing removed entirely still beats the paper model by 0.23.

Those four facts have one mechanism behind them, argued in §5: under FREEZE_ENCODER=1 the 8,192 × 128 entity embedding table is only ever shaped by the pretext task, and in arm B it is never trained at all. The frozen protocol — introduced to make phase 2 a clean test of the representation — is what costs the model 0.31 MRR.

One diagnostic outstanding before this is a finding

jepa_step returns emb_std specifically to catch target-encoder collapse. If it decayed toward zero during arm A's 60 pretraining epochs, then "phase 1 adds nothing" is a training failure, not a property of JEPA — and A ≈ B together with E < C is exactly the signature collapse would produce. The traces have not been pulled yet. §6 says what to run.

§2v19 — what changed and why

v19 · ablation harness
No new configuration, no new model code. One model-selection bug fixed, one regression test added. The six arms are reachable from the existing environment surface alone.

The request

The reviewer asked for an ablation showing how much of the result comes from JEPA pretraining versus any graph encoder — naming two comparators: the same encoder and readout trained from scratch without phase 1, and a plain typed-GNN plus DistMult baseline. Arm C is both of those at once; the remaining arms bracket it.

No new configuration was needed

zero config added Every arm falls out of knobs Config already exposes. JEPA_EPOCHS=0 makes pretrain_jepa's loop body never execute, so it returns a freshly constructed — randomly initialised — encoder. LAYERS=0 builds an empty convs/norms ModuleList, so Encoder.forward falls straight through to type_emb + entity_emb + num_proj(numfeat) with no message passing at all. Both were confirmed by running them end-to-end before the fleet was submitted.

The one code change: best-VAL selection had to snapshot the encoder

fixed train_readout kept the best-VAL scorer and rolled it back at the end, but snapshotted only the scorer. Under FREEZE_ENCODER=1 that is correct and complete — the encoder never moves, so the scorer is the whole model. Every arm that trains the encoder, however, got a best-VAL scorer bolted onto a final-epoch encoder: a pair that existed at no epoch.

The direction of that bug matters. It degrades exactly the arms the JEPA claim is measured against, so leaving it in would have handicapped the baselines and flattered the paper. It is fixed by also deep-copying the encoder state at the selected epoch, guarded on not cfg.freeze_encoder so the frozen path is untouched.

The encoder snapshot is taken only when freeze_encoder is off, so arms A and B run byte-identical code to v18. Four tests fail elsewhere in the suite — test_benchmarks.py (2) and test_clinical_jepa_train.py (2). Confirmed pre-existing by stashing the change and re-running: they are in the clinical_jepa lineage, which v19 does not touch.

§3Results

All runs on the 4,000-graph embedded dataset via Hugging Face Jobs, submitted with --flavor t4-small. Leave-one-out masks exactly one edge and keeps the whole rest of the graph as context; it draws no randomness, so it is exactly reproducible, and it is what the paper reports.

§4Why C and Cp are identical at two seeds

At seeds 42 and 43, arms C and Cp agree to four decimal places on all four metrics, and the collection script downloaded no bytes for those two Cp checkpoints — the Hub's content-addressed storage already had the chunks locally. Both facts point the same way: the files are byte-identical.

This is the best-VAL rollback behaving correctly, not a submission error. Training is deterministic given the seed, so the first 40 epochs of the 100-epoch run reproduce the 40-epoch run exactly. If the best validation AUC falls at or before epoch 40, both runs roll back to the same weights. Seed 44 is the case where the longer run found a better epoch past 40 — 0.8016 against 0.7981 — which simultaneously proves READOUT_EPOCHS=100 was passed through correctly and rules out a plumbing fault at the other two seeds.

A checkpoint cannot tell you which arm produced it

Config.checkpoint_dict writes a hand-picked subset of fields, and jepa_epochs, readout_epochs and freeze_encoder are not among them. Two arms that differ only in those knobs therefore serialise identically. The job logs and the output repository names are the only provenance record for this experiment — keep them.

§5Reading the result

Four separate measurements point at one mechanism, and the mechanism predicts all four.

The frozen protocol is what costs the 0.31

The encoder's input is a sum of three terms: a learned node-type embedding, a learned hashed-entity embedding over 8,192 buckets, and a projection of the demographic and note features. Under FREEZE_ENCODER=1 none of those tables receives a gradient during phase 2. In arm A they are shaped only by the pretext task; in arm B they are never trained at all and remain at their random initialisation for the whole run.

Arms C, Cp and D train them on edge recovery itself. That single difference is worth +0.31 MRR — far more than anything else measured across the v16 → v19 series. The frozen protocol was adopted so that phase 2 would test the representation rather than let the GNN co-adapt to the decoder; it succeeds at that, and the cost of the guarantee turns out to be most of the achievable performance.

D separates memorisation from reasoning

Arm D has no message passing, so its 0.6293 is what learned entity identity alone buys: DistMult over a table that has seen which entities plausibly attach to which relations across 3,200 training admissions. Because leave-one-out ranks the true tail against same-type candidates within the same graph, a strong entity prior — this medication is commonly prescribed, this organism is commonly cultured — does a great deal of the work without any patient-specific reasoning.

The honest decomposition at seed 42 is therefore: 0.6293 from entity memorisation, +0.1624 from message passing on top of it (arm C), and the paper model at 0.3962 below both. Message passing contributes real signal; the paper's pipeline is not the configuration that lets it show.

The JEPA initialisation is worse than random

Arm E takes the pretrained encoder and fine-tunes it — the same freedom arm C has, from a supposedly better starting point. It scores 0.5442 where C scores 0.7917 at the same seed. Pretraining is not merely uninformative for this task; as an initialisation it is 0.2475 MRR worse than random. A representation that were simply neutral would land on top of C, not a quarter of an MRR below it.

That is the observation that makes the collapse check in §6 urgent rather than pedantic. A phase 1 that converged to a degenerate latent space would produce exactly this pattern: no benefit when frozen (A ≈ B), and active harm when used as an initialisation (E < C).

What survives

The graph construction, the typed schema, the evidence pruning, the note localisation and the leave-one-out protocol are untouched by any of this — no arm varies them, so nothing here speaks against them. What does not survive, on the current evidence, is the claim that the JEPA world model is what produces the numbers. Either the contribution is restated around the parts that are actually load-bearing, or phase 1 is fixed and re-measured.

§6What this does not establish

Collapse has not been ruled out — do this first

emb_std is logged every ten epochs by pretrain_jepa and exists precisely to detect a target encoder collapsing to a constant. If it decayed toward zero in the arm A runs, phase 1 never learned anything and the correct conclusion is "the pretraining run is broken", not "pretraining does not help". 

hf jobs ls                                   # find the A-s42/43/44 job IDs
hf jobs logs <job_id> | grep "LATENCY] JEPA"

A healthy run holds emb_std well clear of zero across all 60 epochs. This report's conclusions are conditional on that check.

  • Three seeds is thin for arm C. Its sd is 0.141 and seed 43 sits 0.24 below the other two. The ordering is unanimous across seeds, so the qualitative finding is safe; the effect size is not. Five seeds for C and Cp before a number is quoted.
  • The retrained arm A is below the published number. Seed 42 gives 0.3962 here against the published 0.418653, and the three-seed mean is 0.4027 ± 0.0134. The published value sits about 1.2 sd above that mean — inside the distribution, but at its favourable end. The released checkpoint came from the pre-restructure trainer on different hardware, and docs/EVALUATION.md already records that training is not bit-reproducible above one thread.
  • Entity-identity priors are doing more work than the metric admits. Arm D quantifies this at 0.6293 of achievable MRR. That is a property of the leave-one-out protocol with same-type candidates, and it applies to every number in the v16–v19 series, not only to v19's.
  • Nothing here tests the note localisation. Every arm runs USE_NOTE=1 GROUND_BY=prov. The note's contribution is a v16/v18 question and is unaffected by this ablation.
  • Only pretraining and encoder trainability varied. The pretext task itself (MASK_STRATEGY=random, NODE_MASK=0.4, 60 epochs, the EMA schedule) was not swept. A different phase 1 configuration might behave differently; this measures the one the paper ships.

Recommendation. Pull the emb_std traces. If phase 1 is healthy, report this ablation in full — it is the honest answer to the reviewer, and an unfrozen from-scratch baseline that beats the published pipeline by 0.31 MRR is itself a stronger result than the one the paper currently claims. If phase 1 collapsed, fix it and rerun the 14 jobs before anything is rewritten.

One artifact rule this series learned the hard way

v16's checkpoint carries a config block written by Config.checkpoint_dict — a hand-picked subset of fields. It records hid, use_note, node_mask and sixteen others, but not jepa_epochs, readout_epochs or freeze_encoder. §8v18 — BFS-balanced patch masking

v18 · pretext task
One new module, one branch in jepa_step, two config fields. The default stayed the v17 behaviour, so v18 is opt-in and every earlier gate still runs.

Through v17 the phase-1 mask was i.i.d. Bernoulli: each node masked independently with probability node_mask=0.4, retried until every graph kept at least one target and one context node. The weakness is structural — masking nodes independently leaves a masked node's neighbours almost always visible, so the pretext task can be solved by local interpolation: read the surviving neighbours, average, done. A task solvable one hop out never forces the encoder to learn anything longer-range.

v18 partitions each graph into jepa_patches balanced, connected-ish patches by multi-source BFS and masks whole patches until the node_mask fraction is reached. Targets become coherent regions, so a masked node's neighbours are usually masked too and the shortcut disappears. Keeping the last-drawn patch as context makes the ≥1-target / ≥1-context guarantee hold by construction rather than by retrying. The partition was copied near-verbatim from clinical_jepa/graph/patches.py rather than imported, because tests/test_import_boundaries.py forbids the two lineages from importing each other.

What v19 changes about this reading

Both v18 arms froze the encoder, so the comparison is between two frozen representations. That is internally valid and v19 does not contradict it — but v19 shows the frozen regime itself costs ~0.31 MRR, which is more than an order of magnitude larger than v18's ±0.02 effects. v18 answers "which pretext task yields the better frozen representation"; v19 asks whether the representation should be frozen at all. If phase 1 survives the collapse check in §6, v18's sweep is worth repeating with the encoder unfrozen, where the ranking may not hold.

v18 also ran one seed per cell and said so. v19's three-seed data puts arm A at 0.4027 ± 0.0134, which is the same order as v18's with-note regression of −0.0107 — so that regression remains, as v18 already cautioned, not distinguishable from a single unlucky run.

§9v17 — the refactor, and how it compares to v16

v17 · engineering only
Same model, same numbers to within 1e-6, same environment interface — split into modules, made importable and testable.

no numerics changed v17 deliberately produced no metric movement. It compares to v16 by equality, not by improvement. It is also the release that made both later versions cheap: v18 became a two-field change, and v19 needed no new configuration at all.

What v16 was, and the four problems v17 fixed

  • It configured itself from the environment at import time. Roughly thirty os.environ reads ran when Python imported the module, and NUMERIC_DIM — a tensor shape — was computed at import. Two configurations could not coexist in one process, and the trainer was effectively untestable.
  • Everything shared one namespace. Data loading, the model, both training phases, four evaluators and reporting were interleaved; the standalone evaluate.py reached into trainer.USE_NOTE to validate checkpoints.
  • --help trained the model. main() took no arguments and ran unconditionally, so fawkes-train --help completed a full training run and — with PUSH=1, the default — uploaded the result.
  • The tensor code was hard to read (b, nt, ei, tot_llm), and the checkpoint filename was a hardcoded date stamp.

The split

trainer.py was cut at its own existing comment banners — lines 256 ("shared encoder"), 327 ("downstream readout"), 423 ("EIR scoring") — rather than at invented boundaries, and paper_v16/evaluate.py was folded in as the checkpoint CLI.

Env globals became a dataclass

That is also what let v19 run six configurations from one environment surface without adding a field, and what let its regression test construct Config(jepa_epochs=0, freeze_encoder=False) in-process.

v17 vs v16 — equality, gated three ways
  • Loading the released checkpoint and running loo_evaluate reproduces baseline/paper_loo.json to within 1e-6 on every metric.
  • Encoder().state_dict() and DistMult().state_dict() key sets equal baseline/paper_keys.json — these are attribute paths, so a renamed submodule shows up here and nowhere else.
  • Importing fawkes with no environment set raises no error and reads no os.environ at module scope (AST-verified).

The plan carried an explicit stop rule: if either numeric gate failed, the refactor would be abandoned and trainer.py kept verbatim — "an unverifiable refactor of the paper artifact is not worth the readability gain." The gates passed. Three deliberate behaviour changes shipped, and only three: variant-derived checkpoint names (fawkes_entity_note.pt / fawkes_no_note.pt), CUBLAS_WORKSPACE_CONFIG moved from import into set_seed, and the argument-parse guard that stops --help from training and publishing.

§10v16 — the experiment underneath all of this

v16 · the paper artifact
The entity-grounded-note Graph-JEPA, run 260615. The released checkpoint and every published number come from here.

One hazard to state, because it inverts what the repository name suggests: fawkes is the implementation behind the paper (paper/clinical_jepa.pdf), and clinical_jepa is not — it is the separate modular revision pipeline that v18 borrowed the patch algorithm from. This is documented in docs/LINEAGE.md, stated in both package docstrings, and enforced by tests/test_import_boundaries.py. The "16" is an experiment number from a separate line of work, not the successor to the v5/v6 architecture names in clinical_jepa.

The experiment

A JEPA world model over per-admission clinical knowledge graphs, trained in two phases on 4,000 admission graphs (3,018 subjects, 85,290 LLM edges):

  • Phase 1 — the world model. Masked-node latent prediction, BYOL-style, with an EMA target encoder on one shared encoder. This is the phase v18 changed and the phase v19 ablates away entirely.
  • Phase 2 — the readout. Frozen-encoder edge recovery with InfoNCE over same-type negatives, the four inferred relations upweighted (target_weight=3.0), and the scorer rolled back to its best validation-AUC epoch. v19 corrected that rollback to carry the encoder as well whenever the encoder trains — see §2. The frozen v16 path is unaffected.

v16's own contribution — the thing the "entity-note" name refers to — was localising the Clinical-ModernBERT note vector onto the entity nodes the note actually grounds (28.6% of nodes under ground_by=prov), replacing v15's single per-admission NOTE node. NOTE and HAS_NOTE remain in the vocabulary, unused, as evidence of that retirement. No v19 arm varies this, so nothing in this report speaks for or against it.

The four evaluators

They answer different questions and are not interchangeable. v19 quotes only the first, and disables the third and fourth on every arm to save GPU time:

  • loo_evaluate — mask exactly one edge, keep the whole rest of the graph. No randomness, exactly reproducible. The honest per-relation measure, what the paper reports, and every number in §3.
  • evaluate — batch-mask: 30% of edges held out together. Harder and noisier. Used inside v19's training loop for validation-AUC model selection.
  • cascade_evaluate — recover the inferred relations in order, adding each one's gold edges to context before the next. Disabled in v19 (RUN_CASCADE=0).
  • eir_uplift_eval — refiner precision/recall against v8-gold triples. Off by default; full-gold F1 is hub-dominated.
Where the published number actually comes from

baseline/paper_loo_testsplit.json — MRR 0.418653 over n=8,283, the seeded test split. It reproduces the metrics stored inside the released checkpoint to Δ = 0.00e+00. baseline/paper_loo.json (MRR 0.440249, n=40,000) is not the published number: it is the whole 4,000-record file under the shipped evaluator's >= 2 edge filter with no split, and exists only to gate the evaluator refactor. v19's arm A is measured on the first population, so it is comparable to 0.418653 and not to 0.440249.
