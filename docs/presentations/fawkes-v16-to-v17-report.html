Clinical Graph-JEPA · Engineering Report

fawkes v16 → v17: the same model, provably — better software

What changed between the v16 paper artifact (paper_v16/trainer.py) and the current src/fawkes/ package, and why each change was made. v17 is an engineering release, not a new experiment: no numerics, defaults, or environment-variable names changed, and every claim of equivalence is gated by a recorded baseline.

repo clinical-graph-jepa range f5b1cd6 → 55c27cd + session tooling date 2026-08-04 author Kushagra

§0Orientation: fawkes is the paper implementation

One hazard to state before anything else, because it inverts what the repository name suggests: fawkes is the implementation behind the paper (paper/clinical_jepa.pdf), and clinical_jepa is not — it is the separate modular revision pipeline. The released checkpoint and every reported number come from fawkes, which keeps its original author's name. This is documented in docs/LINEAGE.md, stated in both package docstrings, and enforced by tests/test_import_boundaries.py, which asserts the two packages never import each other.

"v16" below means the frozen experiment paper_v16 (run 260615): the entity-grounded-note Graph-JEPA, where the Clinical-ModernBERT note vector is localized onto the entity nodes the note actually grounds. "v17" means the current state of src/fawkes/.

§1What v16 was, and why it had to change

v16 lived almost entirely in one file: paper_v16/trainer.py, 719 lines, plus a separate checkpoint-only evaluate.py. It produced the released checkpoint and the published metrics — and it had four structural problems, each of which motivated a specific part of the restructure:

  • It configured itself from the environment at import time. Roughly thirty os.environ reads ran when Python imported the module, and NUMERIC_DIM — a tensor shape — was computed at import. Consequences: environment variables had to be set before the import (hence the env-prefixed commands in the README), two configurations could not coexist in one process, and the trainer was effectively untestable.
  • Everything shared one namespace. Data loading, the model, both training phases, four evaluators, and reporting were interleaved in a single module; the standalone evaluate.py reached into it (trainer.USE_NOTE) to validate checkpoints, coupling the CLI to the import-time globals.
  • --help trained the model. main() took no arguments and ran unconditionally, so fawkes-train --help completed a full training run — and, because PUSH defaults to 1, uploaded the result to the Hugging Face OUTPUT_REPO.
  • The code was hard to read. Single-letter and abbreviated names (b, nt, ei, tot_llm) throughout the tensor code, and a hardcoded, date-stamped checkpoint filename (fawkes_trainer_jepa_entity_note_v16_260615.pt) at line 704.

The restructure plan (docs/RESTRUCTURE_PLAN.md §5) called this the highest-risk phase of the whole repository restructure, because the file backs the paper: "Splitting it risks silent reproducibility drift in the one artifact that backs the paper." That risk shaped everything in §3 below.

§2The split: one module per concern

trainer.py was split at its own existing seams — the comment banners at lines 256 ("shared encoder"), 327 ("downstream readout"), and 423 ("EIR scoring") — rather than at invented boundaries. The standalone paper_v16/evaluate.py was folded into fawkes/evaluate.py as the checkpoint CLI at the bottom of that module.

v17 moduleContentsCame from
config.py Config — every experiment knob; from_env(), from_checkpoint(), checkpoint_dict(), checkpoint_name the ~30 import-time env globals
data.py vocabularies, score_vec, load_full_dataset, to_data trainer.py data section
model.py Encoder, JEPA, DistMult, Scorer trainer.py "shared encoder" seam
steps.py per-batch tensor work: jepa_step, readout_step, valid_mask, buckets, negative sampling extracted later from train.py — see §5
train.py the run: set_seed, data prep/split, both training phases, reporting, main trainer.py spine
evaluate.py evaluate, loo_evaluate, cascade_evaluate, eir_uplift_eval, shared ranking helpers, checkpoint CLI trainer.py lines 382–579 + paper_v16/evaluate.py

The four evaluators answer different questions and are deliberately kept side by side rather than merged: evaluate is batch-mask recovery (30% of edges held out together); loo_evaluate masks exactly one edge with the whole rest of the graph as context — no randomness, exactly reproducible, and what the paper reports; cascade_evaluate recovers the inferred relations in order, feeding each one's gold edges to the next; and eir_uplift_eval measures refiner precision/recall against v8-gold triples. What they share — the ranking protocol (same-type candidates in the same graph, filtered ranking, ties favoring the true tail) — was factored into helpers at the top of the module instead of being copied four times.

§3The config refactor: env globals become a dataclass

This is the substantive design change of the release. Every import-time global became a field on a frozen-by-convention Config dataclass, and the environment is now read only on demand by Config.from_env() — with the same variable names, the same defaults, and the same parsing rules (including the truthiness rule "1"/"true"/"yes" for every boolean). The documented invocations work unchanged, and importing the package has no side effects — asserted by an AST walk in tests/test_fawkes.py.

NUMERIC_DIM became the numeric_dim property (BASE_NUMERIC + embed_dim if use_note else 0) — the tensor shape is now derived from a value you hold, not from whatever the environment happened to say at import. Two smaller pieces round out the config story:

  • checkpoint_dict() writes a hand-picked subset of fields into the checkpoint (deliberately not asdict() — the released checkpoint carries exactly these keys), and Config.from_checkpoint() rebuilds the architecture-relevant fields from a saved checkpoint, which is what lets a released checkpoint load without setting a single environment variable.
  • The fawkes-eval CLI still refuses to run when use_note / ground_by / embed_dim / use_scores disagree with the checkpoint's saved config — the v16 guard, kept, because those four fields change the architecture (e.g. use_note flips the encoder input projection between 6 and 774 features).

§4What did not change — and how that is proven

unchanged No numerics, no defaults, no tensor operations, and no environment-variable names. This was the plan's hard constraint, and it is not taken on faith: before the restructure began, Phase 0 froze the old tree beside the new one as an oracle — never edited, not even to import from the new code — and recorded its behavior into baseline/*.json. Every fawkes module is gated against those recordings by tests/test_fawkes.py.

Phase 5 gates — all passed
  • Loading the released checkpoint and running loo_evaluate reproduces baseline/paper_loo.json to within 1e-6 on every metric.
  • Encoder().state_dict() and DistMult().state_dict() key sets equal baseline/paper_keys.json — attribute paths, which survive class renames but not attribute renames, so this catches exactly the kind of drift a refactor risks.
  • Importing fawkes with no environment variables set raises no error and reads no os.environ at module scope (AST-verified).

The plan also carried an explicit stop rule: if either numeric gate could not be met, the refactor would be abandoned and trainer.py kept verbatim inside the package — "an unverifiable refactor of the paper artifact is not worth the readability gain." The gates passed, so the split stood. Phase 8 then deleted the old tree, having first recorded what it produced into baseline/; baseline/COVERAGE.md lists every gate that lost its oracle in that deletion and what covers the live half now. Checkpoint files also kept their exact names, which keeps every sha256 in models/MANIFEST.json byte-stable and makes the model-directory renames provably content-neutral.

§5The deliberate behavior changes

changed Three, and only three, intentional differences in behavior — each small, each with a reason:

1. New checkpoints get variant-derived names

New runs save fawkes_entity_note.pt (USE_NOTE=1) or fawkes_no_note.pt (USE_NOTE=0), replacing the hardcoded fawkes_trainer_jepa_entity_note_v16_260615.pt. Why: the date stamp is what made the old name unreadable, and provenance already lives in git history and models/MANIFEST.json; the name now encodes the one thing that matters for loading — which architecture variant the file contains. Existing checkpoint files keep their names and load unchanged; the Hugging Face upload path uses the same new name.

2. CUBLAS_WORKSPACE_CONFIG moved from import to set_seed

The original set it at module import with the comment "MUST precede import torch." What actually matters is that it precedes the creation of the first cuBLAS handle; set_seed runs at the top of main, before any tensor work, so the deterministic-kernels effect is unchanged — and the package stays importable without touching the environment.

3. --help can no longer train and publish

fawkes-train now parses arguments before doing anything else, through a parser that deliberately accepts no options (the experiment is configured entirely from the environment). --help prints usage and exits; an unrecognized flag is an error. In v16, either of those would have started a full training run and — with PUSH=1, the default — uploaded a checkpoint to the Hub.

§6Post-split refactors: the two August commits

With the baseline gates in place, two further passes cleaned the code the split had preserved verbatim. Both are pinned by the same test strategy — tests/test_fawkes.py holds the training steps bit-for-bit against the recorded trainer — so they are refactors in the strict sense.

3fca89f — variable naming

Systematic renames across data.py, evaluate.py, model.py, and train.py (~600 lines touched): b → batch, nt → node_type, ng → num_graphs, tot_llm → total_llm, no_ev → no_evidence, and so on. Signatures became self-documenting — same_type_k(targets, node_type, batch_index, order, sorted_buckets, num_neg) instead of same_type_k(targets, nt, bt, o, sb, K) — with no logic changes.

55c27cd — structural refactoring

  • steps.py extracted (209 lines): the per-batch tensor work — jepa_step, readout_step, valid_mask, buckets, negative sampling — moved out of train.py. The concrete reason: evaluate.py reuses readout_step and buckets, which previously forced a circular import that train.main worked around with a deferred import. The cycle is now simply gone.
  • train.py decomposed from one long main into named stages that read like the experiment's outline: prepare_data (load → audit vocab → convert → seeded split), pretrain_jepa (Phase 1, the JEPA world model), train_readout (Phase 2, frozen-encoder edge recovery with best-VAL-AUC selection), then the reporting helpers (_report_test, _report_loo, _run_cascade, _run_eir) and _save_and_push.
  • evaluate.py reorganized around the shared ranking helpers, with the four-evaluators contract written into the module docstring so the next reader doesn't have to reverse-engineer which number is "the honest one" (it's LOO).

§7New tooling: training on Hugging Face Jobs

new Two PEP 723 uv scripts (currently uncommitted) let a full fawkes run execute on Hugging Face Jobs hardware with no changes to the training code — possible precisely because of §3: the trainer is configured by plain environment variables and already pulls its dataset from, and pushes its checkpoint to, the Hub.

  • scripts/launch_fawkes_hf_job.py — run locally. Because the GitHub repository is private, a job cannot pip install the code from git; the launcher instead uploads src/fawkes (stamped with the git SHA) to a private Hub model repo, then submits the job via run_uv_job, forwarding the caller's HF_TOKEN as an encrypted secret. It also redirects OUTPUT_REPO to the caller's namespace — the config default points at wmatbooth/…, which the job's token cannot push to, and would otherwise fail only after a complete training run.
  • scripts/hf_job_fawkes_train.py — runs on the job. Declares the runtime dependencies inline, downloads the code repo, puts it on sys.path, and calls the unchanged fawkes.train.main.

Configuration passes through unchanged: -e USE_NOTE=0 submits the no-note variant, and a cheap smoke run is -e JEPA_EPOCHS=2 -e READOUT_EPOCHS=2 -e LOO_CAP=200 -e RUN_CASCADE=0 -e PUSH=0. Defaults: t4-small hardware (the model is small — a 2-layer encoder at hid=128) and a 2-hour timeout, since the platform default is only 30 minutes.

§8Summary

v17 is what v16 looked like all along to the person who wrote it, made legible to everyone else: the same experiment, the same numbers to within 1e-6, the same environment interface — now importable without side effects, testable with two configurations in one process, split into modules that match the experiment's actual phases, named so the tensor code can be read, guarded so --help is harmless, and runnable end-to-end on rented hardware with one command. The three behavior changes (checkpoint naming, where the cuBLAS flag is set, the argument-parse guard) are each documented at the point in the code where they happen.
