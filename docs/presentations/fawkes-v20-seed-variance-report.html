Clinical Graph-JEPA · Engineering Report No. 4

v20: how much of Table 1 is the seed?

A reviewer asked for mean ± std across seeds and splits, on the grounds that the paper reports one particular random sample of patients. v20 answers the seed half: ten retrains of the paper configuration on the published split. The published number survives — but the error bar it needs is wider than the effects the paper compares. §7–§10 then work backwards through v19, v18, v17 and v16 so the lineage stays traceable from one document.

repo clinical-graph-jepa runs 10 (1 arm × 10 seeds) eval LOO 8,283 · batch-mask 3,000 seeds 42–51 split 42, fixed lineage v16 → v20 date 2026-08-06

§1The verdict, first

The published number is not a lucky seed, and it is also not reproducible as a point. Ten retrains of the exact paper configuration, differing only in training seed, give LOO MRR 0.4174 ± 0.0190. The published 0.418653 sits essentially on that mean — inside the 95% confidence interval for all four metrics, at the 40th percentile of the ten draws. Nothing about Table 1's headline was cherry-picked.

What the sweep does establish is that the error bar is large. Seed alone moves MRR across a range of 0.061 and Hits@1 across 0.072 — a coefficient of variation of 9.4% on Hits@1. Any comparison in Table 1 whose margin is smaller than roughly 0.024 MRR is not distinguishable from seed noise at this sample size.

Against a comparably-seeded baseline at n = 10 per arm. Below this, a Table 1 gap cannot be claimed as real.

The same holds on the other evaluation protocol. Each checkpoint carries a second metric block — the batch-mask evaluation, the only one that computes AUC — and every one of its metrics also lands inside the ten-seed 95% CI. AUC comes out at 0.7145 ± 0.0186 against a published 0.714351: a difference of 0.0002, or 0.01 sd. Eight metrics across two protocols, and none of them contradicts the paper.

The evaluation population is byte-identical to the paper's

Every run reports quiz_sig = 304815655090 — and so does the released v16 checkpoint. That signature hashes the evaluation questions themselves, so the ten retrains were asked exactly the same questions as the published model, on exactly the same 8,283 LOO edges and 3,000 ranked batch-mask queries. Whatever moves between these runs, the measuring instrument does not.

The reviewer's question is only half answered

The review asked for variance across seeds and splits, and named the patient sample specifically. All ten runs here share DATA_SPLIT_SEED=42, so every one of them holds out the same 400 admissions. This report measures initialisation variance and says nothing about sensitivity to which patients were sampled. §6 states what is still missing and what it costs.

§2v20 — what changed and why

v20 · split/seed separation
One config field, one line in the splitter, one regression test. No model code, no change to any published number — the defaults describe the same experiment they always did.

One knob was doing two jobs

Before v20, _split_items keyed its permutation on cfg.seed — the same value set_seed hands to torch.manual_seed and np.random.seed. Changing SEED therefore resampled the test set and reinitialised the model at once, and the two effects could not be separated. That is exactly the separation the review asks for.

+1 config field data_split_seed defaults to 42, as does seed, so Config() and an unset environment describe the same experiment they described in v16. It is read from DATA_SPLIT_SEED by Config.from_env and printed on both the [ENTRY] and [DATA] log lines, so a job log now records which cohort it trained on.

Why it is not in the checkpoint

deliberate omission checkpoint_dict() writes a hand-picked subset of fields that test_checkpoint_dict_matches_released_config pins byte-for-byte against the released v16 file. Adding a key breaks that gate. data_split_seed therefore lives in the output-repository name and the job log — the same provenance convention v19 was forced into for its arms (§8).

Verification

Counts cannot prove a split is pinned: TRAIN=3200 VAL=400 TEST=400 is a function of the fractions, identical for every seed. Membership was compared directly, by gid, on the real 4,000-admission dataset.

The published split is provably unmoved

All nineteen fawkes gates pass, including test_loo_reproduces_published_test_split, which rebuilds the split, runs LOO with the released checkpoint and reproduces baseline/paper_loo_testsplit.json to 1e-6. The new gate, test_split_follows_data_split_seed_not_seed, asserts the split holds under a changed seed and moves under a changed data_split_seed; it fails against the old cfg.seed code path, so it is a real gate rather than a vacuous one.

One consequence to know about: SEED alone no longer moves the split, so re-running submit-v19-ablations.sh unchanged now produces three runs that share split 42 and differ only in initialisation — not the semantics that produced the recorded v19 numbers. That script was deliberately left untouched.

The ordering is not incidental. Hits@1 is the least stable metric in Table 1, by roughly an order of magnitude over the steadiest. A top-1 metric changes whenever a single ranking flips at the boundary, while Hits@10 is close enough to saturation (0.87) that the same flips rarely cross it. The second panel carries a finding worth its own sentence: the same MRR is 4.4× more stable under batch-mask evaluation than under LOO — sd 0.0043 against 0.0190 — even though LOO scores 8,283 queries and batch-mask only 3,000. More queries normally means a tighter estimate, so the difference is not sampling noise; it is the protocol. A plausible reading is that LOO's full-context setting produces sharper, more confident rankings, so a small change in weights reorders many near-ties at the top, while batch-mask's degraded context flattens the rankings and damps that effect. That is a hypothesis this data does not test, and it does not change which number the paper reports — but if a tighter error bar is wanted for a secondary table, the batch-mask block already provides one.

§4Why seed 42 does not reproduce the published number

The collection script checks the sp42-s42 cell against the published 0.418653, on the reasoning that it is the same configuration at the same seed on the same split. It came back 0.3962, Δ −0.0225. That check was too strict, and the reason matters more than the miss.

0.418653 is the released checkpoint's own metric, not a retraining target. baseline/paper_loo_testsplit.json is produced by loading models/fawkes-entity-note/…v16_260615.pt and evaluating it — a path that reproduces to Δ = 0.00e+00 and still does, under test_loo_reproduces_published_test_split. The v20 runs do something different: they train a new model from scratch on a T4 with torch==2.4.1. Seed equality gives an identical split, and §2 proves it does, but it does not give identical weights across different hardware and library versions.

Determinism here is requested, not guaranteed

set_seed calls torch.use_deterministic_algorithms(True, warn_only=True). The warn_only flag means any operation without a deterministic implementation falls back to the non-deterministic kernel and logs a warning instead of raising. The scatter reductions underneath TransformerConv are exactly such operations on CUDA. Run-to-run variation at a fixed seed is therefore expected on GPU, and two runs of sp42-s42 on the same T4 need not agree either — a cheap follow-up that would bound this directly.

This is why the mean is the reproduction check and the single cell is not. If something had genuinely drifted — a regression in the v18 patch-masking refactor, the v19 encoder-snapshot change, a data path — the whole distribution would move. Instead the ten-seed mean lands 0.0012 from the published value. The seed-42 cell is simply the second-lowest of ten draws, at z = −1.12, which at n = 10 is unremarkable.

The practical correction: print_v20_seed_variance_table.py's published-run line should be read as a distributional check, not an equality gate. A single cell within about 2 sd of the published value is consistent; the mean landing far from it would be the alarm.

No retrain in this lineage has ever reproduced the published number

Worth stating explicitly, because it is easy to believe otherwise. Every apparent reproduction of 0.418653 in Reports No. 1–3 is a re-evaluation of the released checkpoint: baseline/paper_loo_testsplit.json, the test_loo_reproduces_published_test_split gate, and — as §9 shows — the baseline column of v18's comparison table, which matches the published file on all four metrics to four decimal places. Those paths reproduce to Δ = 0.00e+00 because they load the same weights.

v20 is the first time the paper configuration has been retrained from scratch at any scale. That it lands 0.0012 from the published value in the mean is the reproduction result; that no individual seed lands on it is the expected behaviour of the training pipeline, and was simply never visible before.

Keep the two blocks visibly separate in the paper, as above. They are different protocols and their MRR columns differ by 0.055 — a reader who sees one MRR beside an AUC will assume they came from the same evaluation.

Report the standard deviation rather than the standard error, and state n explicitly. With ten runs the sd is itself only known to about ±24%, so quoting it to more than two significant figures overstates what was measured. Naming the seed range in the text — "seeds 42–51" — costs a clause and forecloses the question of whether the set was chosen after seeing results.

What can and cannot be claimed

Against a baseline run with the same ten-seed protocol, the smallest difference detectable at α = .05 with 80% power is about 0.024 LOO MRR — 5.7% of the mean. Every metric has its own threshold, and they are not interchangeable:

The ten runs share one split, which makes them paired — same held-out admissions, same 8,283 queries, same denominator. A paired test across seeds is therefore legitimate and is the right instrument for any arm-versus-arm comparison run the same way. That pairing is precisely what is lost the moment the split varies, which is the subject of §6.

This also re-frames v19

v19 concluded that JEPA pretraining is indistinguishable from random initialisation, on a B − A mean of −0.008 across three seeds. The seed noise measured here is 0.019 sd on a single arm — more than twice that margin. v19's negative result is strengthened by this: the effect it failed to find is well below what three seeds could have resolved. v19's large positive effects (+0.311 for from-scratch training) are far outside the noise and stand unaffected.

§6What this does not establish

The split axis is unmeasured

This is the important one. The review asked about which patients were sampled, and every run in this report held out the same 400 admissions. The data_split_seed machinery to answer it now exists and is tested; it simply has not been run. Four additional jobs would give five splits at seed 42 alongside the existing seed sweep, sharing the sp42-s42 cell: 

for split in 43 44 45 46; do submit $split 42 4h; done

Expect that spread to be larger than the seed spread, not smaller: a new split changes the held-out admissions, the query population and the denominator all at once. Those runs are also not paired with each other, so they yield a spread to report, never a paired test.

The split is by admission, not by patient

Investigating the membership check surfaced a property of the split that predates v20 and is worth stating plainly, because the same reviewer is the one most likely to find it. _split_items permutes admission-level records, and the 4,000 admissions come from only 3,018 subjects.

But over a third of the evaluation set belongs to a patient the model has already seen, and a grouped split — patients as the unit, not admissions — is a roughly ten-line change to _split_items. It would almost certainly move Table 1 downward, which makes it a decision about the paper rather than a bug fix, and it deserves to be made deliberately rather than discovered in review.

Smaller limits

  • One configuration only. These ten runs are the paper arm. The seed noise of a different architecture is not assumed to be 0.019 — v19's arm C showed sd 0.141 across three seeds, seven times larger.
  • Cascade and EIR metrics are absent. All ten ran with RUN_CASCADE=0 and RUN_EIR=0, so those checkpoint blocks are empty. LOO and batch-mask are the two protocols covered here; if Table 1 carries cascade columns they need their own sweep.
  • The sd is itself uncertain. At n = 10 its relative standard error is about 24%; the true sd could plausibly be 0.014 or 0.024.
  • Fixed-hardware determinism was not tested. No seed was run twice on the same flavour, so the floor of run-to-run variation is unmeasured (§4).

The artifact rule this series keeps re-learning

§8v19 — the JEPA pretraining ablation

v19 · ablation harness
No new configuration, no new model code. One model-selection bug fixed, one regression test added. Six arms reachable from the existing environment surface.

A reviewer asked how much of the fawkes result comes from JEPA pretraining rather than from having any graph encoder at all. Six arms across three seeds answered it, and the answer was not the one the paper assumes: a frozen randomly initialised encoder scores the same as the JEPA-pretrained one (B − A ≈ −0.008, sign flipping across seeds), while the identical architecture trained end-to-end without phase 1 beats both by roughly 0.31 MRR. An encoder with message passing removed entirely (LAYERS=0) still beat the paper model by 0.23.

The mechanism v19 proposed: under FREEZE_ENCODER=1 the 8,192 × 128 entity embedding table is only ever shaped by the pretext task, and in arm B never trained at all. The frozen protocol — introduced to make phase 2 a clean test of the representation — is what costs the model 0.31 MRR.

v19's one code change was in train_readout: best-VAL selection snapshotted only the scorer, so every arm that trains the encoder got a best-VAL scorer bolted onto a final-epoch encoder — a pair that existed at no epoch. The bug degraded exactly the arms the JEPA claim is measured against, so leaving it in would have flattered the paper. The frozen path was provably untouched, which is why arms A and B ran byte-identical code to v18.

v19's outstanding diagnostic, still outstanding

jepa_step returns emb_std specifically to catch target-encoder collapse. If it decayed toward zero during arm A's 60 pretraining epochs, "phase 1 adds nothing" is a training failure rather than a property of JEPA — and A ≈ B together with E < C is the signature collapse would produce. Those traces have still not been pulled. v20 does not bear on this either way.

§9v18 — BFS-balanced patch masking

v18 · pretext task
One new module, one branch in jepa_step, two config fields. The default stayed the v17 behaviour, so v18 is opt-in and every earlier gate still runs.

v16's pretext task masks nodes i.i.d. Bernoulli at NODE_MASK=0.4. v18 added MASK_STRATEGY=patch: patches.py partitions each graph into JEPA_PATCHES=8 BFS-balanced patches and masks whole patches, so the model cannot infer a masked node from its immediate neighbours. This matches what clinical_jepa does and what the paper's schematic depicts.

There is a second problem the baseline column exposes. The with-note comparison sets a freshly trained patch-mask model against the released checkpoint, so the two cells differ by more than the pretext task — they differ by an entire training run, on different hardware, at a different time. v20 puts the width of that difference at ±0.019 on its own. The −0.0107 regression is therefore not just underpowered; it is not a paired comparison in the first place. Repeating v18 should retrain both arms.

§10v17 and v16 — the refactor and the experiment underneath

v17 — the refactor that had to move nothing

paper_v16/trainer.py was 719 lines that read roughly thirty os.environ values at import time and computed NUMERIC_DIM — a tensor shape — from them. Environment variables had to be set before Python imported the module, two configurations could not coexist in one process, and the trainer was effectively untestable. v17 split it into fawkes/{config,data,model,steps,train,evaluate}.py and turned every global into a Config field, with Config.from_env() reading the same names, the same defaults and the same parsing rules.

The success criterion was equality, not improvement: LOO metrics to 1e-6, identical state_dict key sets, and an AST-level gate proving no module-scope environment reads remain. All three still pass under v20.

v16 — the experiment that produced the published number

v15 attached the Clinical-ModernBERT note embedding to a single per-admission NOTE node. v16 retired that node and localised the same 768-dimensional vector onto the entity nodes the note actually grounds — by default the endpoints of any edge carrying prov_in_note. Ungrounded entities receive a zero vector. On the shipped dataset this puts the note on 28.6% of nodes.
